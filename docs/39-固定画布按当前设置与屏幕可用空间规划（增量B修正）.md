# 39 · 固定画布「按当前设置 + 当前屏幕可用空间」规划（增量 B 修正）

> 本文件**取代** `docs/38-Windows轮盘菜单移植（增量B）交付说明.md` §10 里
> 「按设置上限预留固定画布」的结论。§10 所述的 `2054.7 × 2054.7` 常驻画布
> **已被操作者否决，不再使用**。
>
> `docs/38` 的其余部分（菜单树、动作 ID、几何与 Region 规则、动画参数、主题色值）
> 仍然有效。

---

## 1. 为什么修

增量 B 第一版为了满足「拖动任何轮盘设置滑块都不改变窗口矩形」，把画布按
`preferredScale / buttonVisualScale / menuDistance` 的**上限**
（`2.50 / 2.50 / 0.30`）预留，结果一个 256px 的桌宠也要一块
`2054.7 × 2054.7` 的常驻透明窗口 —— 在 1920×1040 工作区上明显不可接受。

操作者的裁决（原文口径）：

> 不按所有设置上限预留固定画布。
> 也不按默认档永久固定并让极端档裁切。
> 改为：**按当前设置 + 当前显示器可用空间计算固定画布；菜单开关与层级切换期间
> HWND Rect 恒定；仅当几何设置或桌宠可见尺寸改变时，在菜单关闭状态下原子重建固定画布。**

---

## 2. 新口径（一句话）

```
画布尺寸 = f(当前轮盘设置, 当前桌宠可见尺寸, 当前显示器工作区)
```

* **当前设置**参与计算（不再取上限）；
* 屏幕放不下时，用 **Android 自己的设备级应急缩放**
  （`WheelMenuGeometry.deviceEmergencyScale` 同一口径）压缩轮盘；
* 菜单开 / 关 / 换层 / 悬停 / 滑动 / 按压 / 右键菜单期间 **HWND Rect 恒定**；
* 只有「几何设置变化 / 桌宠尺寸变化 / 显示器或 DPI 变化 / 面板返回桌宠」才在
  **菜单关闭态**原子重建一次。

新增模块：`lib/menu/wheel_canvas_plan.dart`（纯 Dart，可 `flutter_tester` 单测）。

## 3. 画布计算输入（逐项对齐决策一）

| 输入 | 取值来源 |
|---|---|
| 当前 normalized `wheelScale` | `AppSettings.wheelLayoutSettings.preferredScale` |
| 当前 normalized `buttonVisualScale` | 同上 `.buttonVisualScale` |
| 当前 normalized `menuDistance` | 同上 `.menuDistance` |
| 当前桌宠可见宽高 | `petSize()`（= 素材尺寸 × 缩放） |
| 当前主题下的描边 / 文字安全带 | `WheelMenuSpec.fromDensity(1.0)`（`outlineDp 2.2`、`safetyPaddingDp 10`、`WheelTextLayout`） |
| 当前版本最大菜单项数 | `MenuCatalog.maxItems`（当前 = 7） |
| 左右两种展开方向 | `WheelExpandDirection.values`（2）× `WheelVerticalMode.values`（3）共 **6 次**测量 |
| 当前显示器 workArea | `FixedCanvasWindowOps.displayForPoint()` 返回的 `WheelDisplayArea` |
| Android 设备级应急缩放规则 | `WheelMenuGeometry.deviceEmergencyScale` + `minActualScale = 0.60` |

**已删除**的旧输入（不再使用）：`wheelScale` 上限 2.50 / `buttonScale` 上限 2.50 /
`menuDistance` 上限 0.30，以及由此产生的常驻最大窗口。
`lib/menu/wheel_canvas_bridge.dart` 里的 `reachBudget / canvasSizeFor / layoutForPet /
petAnchorFor` 已随之删除 —— 该文件现在**只**做「屏幕坐标 → 画布局部坐标」的平移。

### 测量方法（不新造任何视觉常量）

`WheelCanvasPlanner.measureReach()` 把桌宠放在一块**虚拟大屏**
（`±1e6`）的原点，对「左右 2 方向 × 竖直 3 模式」各跑一次 **Android 原版**
`WheelMenuGeometry.computeEnvelope`，再取四侧最大外扩量
（`reachLeft / reachRight / reachUp / reachDown`）。因为虚拟大屏足够大，结果里
既没有窗口夹取、也没有应急缩放 —— 纯几何量。

```
canvas.width  = pet.width  + reachLeft + reachRight + 2 × margin(8)
canvas.height = pet.height + reachUp   + reachDown  + 2 × margin(8)
petAnchor     = (reachLeft + margin, reachUp + margin)     // 左右对称 → 桌宠居中
```

## 4. 稳定性范围（决策二）

窗口 Rect **完全不变**（`windowOps.commitBounds` 调用次数 0）：

打开轮盘 / 关闭轮盘 / 根菜单与子菜单切换 / 返回 / 悬停 / 圆弧滑动 / 按压 /
选中反馈 / 右键菜单开关。

允许**重新计算一次**画布（唯一一次 `SetWindowPos`）：

| 触发 | 说明 |
|---|---|
| `wheelScale` 改变 | 设置页滑块 |
| `buttonScale` 改变 | 设置页滑块 |
| `menuDistance` 改变 | 设置页滑块 |
| 桌宠素材可见尺寸 / 桌宠缩放改变 | `petSize()` 变化 |
| 显示器 / DPI 改变 | 工作区尺寸变化（下次重建生效） |
| 从控制面板返回桌宠模式 | 外壳 `commitFixedCanvasBounds` 走同一规划器 |

`FixedCanvasProbeState.isCanvasPlanStale` 是判据：桌宠尺寸或三个几何设置任一变化
即视为过期。**直接点击桌宠打开菜单时如果计划已过期**，会先在关闭态重建一次再打开，
保证这次打开的画布一定装得下按当前设置绘制的轮盘。

## 5. 重建事务（决策三，逐步实现）

`FixedCanvasProbeState._rebuildFixedCanvas(reason)`：

| 步骤 | 实现 |
|---|---|
| 1 | 轮盘打开 / 过渡中 → 先 `close(animate: false)`，等 Region 收敛到 pet |
| 2 | `windowsSurfaceSession.changeTo(transitioningToPet)` |
| 3 | `windowOps.setVisible(false)` |
| 4 | 读当前桌宠屏幕锚点（旧计划 + 旧 `currentBounds()` 换算） |
| 5 | 用当前设置重新 `WheelCanvasPlanner.plan(...)` |
| 6 | 工作区来自 `displayForPoint`，应急缩放含在 plan 里 |
| 7 | **一次** `commitBounds(...)`（= 一次 `SetWindowPos`） |
| 8 | `petAnchor = petScreen − safeRect.topLeft` → 桌宠屏幕锚点**不变** |
| 9 | `endOfFrame` 后应用 pet-only Region（经 `RegionCoordinator`，owner=pet） |
| 10 | 回读 `currentBounds` / Region 包围盒 / `petScreenRect` 并算误差 |
| 11 | 校验通过（Region ok + 锚点误差 ≤ 1px + 窗口与请求一致）才 `setVisible(true)` |
| 12 | 失败 → `_restoreCanvasPlan()` 回到最近一次有效计划（旧画布矩形 + 旧锚点） |

* 模式切换用的就是既有枚举 `WindowsSurfaceMode.transitioningToPet`
  （`allowsFixedCanvasCommit = true`、`isPetLike = true`、非 panel-like），
  收尾无条件回到 `petFixedCanvas`；因此**没有新增枚举值、没有改模式机语义**。
* 事务串行：`_rebuilding` 标志保证同一时刻只有一个；`_onExternalChange` 期间
  也会忽略重复信号。
* 可观测：`canvasRebuildCount` / `canvasRebuildFailures` /
  `lastRebuildAnchorErrorPx`，日志 `wheel.canvas.rebuild` /
  `wheel.canvas.rebuild.failed` / `wheel.canvas.rebuild.exception`。

> **接口变更**：`FixedCanvasWindowOps` 新增 `Future<void> setVisible(bool)`。
> 生产实现 = `windowManager.show()/hide()`（`WindowsFixedCanvasWindowOps`）；
> 测试注入假实现。它**只**服务于本重建事务，开合菜单期间绝不调用。

## 6. 显示器约束（决策四）

```
limit = min(workArea × 1.06, workArea + 48px)         // 逐维，且不低于桌宠尺寸
```

* 默认目标：**画布宽高不超过工作区**；`+6% / +48px` 是"明确上限"里的少量越界额度；
* 二分（24 步）求**最大**的 `screenFactor ∈ [minActualScale(0.60), 1]`，
  使 `canvas(screenFactor) ≤ limit`；`canvasAt(k)` 对 `k` 单调不减，二分正确；
* `effectiveScale = clamp(wheelScale × screenFactor, 0.50, 2.50)`；
  该值**只**回填到轮盘信封的 `preferredScale` —— 按钮倍率与菜单距离仍是用户原值；
* 压到 `0.60` 仍超出 → 画布夹到 `limit` 并标记 `truncated`，提示
  「轮盘已压到最小仍超出屏幕可用空间，已按当前屏幕自动压缩」；
* 命中区域下限由 Android 自己的数学保证，未引入新常量：
  `buttonTouchDiameterPx ≥ buttonTouchMinDp(48)`、`ringRadius ≥ spec.dp(minRadiusDp)`。

### emergencyScale 触发条件

> 逐维判断：`canvasAt(1.0).width > limit.width` **或** `canvasAt(1.0).height > limit.height`
> （即"按当前设置、不做任何压缩"的画布超过 `min(workArea×1.06, workArea+48)`）。
> 触发后 `screenFactor < 1`，`compressed = true`，`reason = 'screen-fit'`。
> 若连 `screenFactor = 0.60` 都不够 → `truncated = true`，`reason = 'screen-truncated'`。

### 关于「压缩优先级」的说明（如实记录）

决策四给出的是「1 轨道与文字安全带 → 2 按钮间距 → 3 轮盘视觉缩放」的顺序。
**Android 没有暴露分别控制这三者的旋钮**，且本次不允许新造视觉常量，
因此实现采用 Android 自己的均匀应急缩放：一个 `screenFactor` 同时作用于
按钮直径、环带半径、刀刃长度与整个绘制包围盒（= 决策四的 2 与 3 同时收缩），
而 `bandPaddingDp(8)` / `rimLobeDp(7)` 这类 Android **固定常量**不参与压缩，
它们本身只有个位数像素量级，不构成"放不下"的主因。
这一取舍写在这里，供后续按需改成真正的分级压缩。

## 7. 设置语义（决策五）

设置页「轮盘大小」行现在显示：

```
轮盘大小  250%
[滑块]
范围 50% ~ 250%，步进 10%，默认 100%
当前屏幕实际显示：169%
原因：受当前显示器可用空间限制（请求 250%）
保存的仍是所选值；换到更大的显示器会自动恢复更大的实际值
```

* `WheelCanvasFit`（`WheelCanvasFit.requestedScale / effectiveScale / compressed /
  truncated / screenFactor / canvasSize / workArea / petSize`）由探针写入模块级
  `wheelCanvasFit`（`ValueNotifier`），设置页只读；
* 设置页还会用 broadcast 里的 `petSize + workArea` **本地重算一次**
  （`WheelCanvasPlanner.plan`），所以在控制面板里拖动滑块时数值**不滞后**；
* 未压缩时显示「当前屏幕实际显示：100%（未触发屏幕适配压缩）」；
* **持久化永远保存用户值**（`AppSettings.normalized()` 不变，只夹取/量化，
  不做屏幕适配压缩），因此换大屏后实际值自动变大。

## 10. 已知限制（如实记录）

1. **`truncated` 的物理极限**：当"桌宠本身 + 四侧预留"已经大于工作区时
   （例如 512px 桌宠在 1040 高的屏上、或 250% 轮盘在 720p 屏上），把
   `screenFactor` 压到 Android 下限 `0.60` 仍然放不下。此时画布夹到
   `limit`、UI 提示「已按当前屏幕自动压缩」，轮盘最外圈的装饰（刀刃尖端 /
   文字 chip）会被 `clampToCanvas` 裁掉，按钮仍可命中。
   缓解手段（用户可操作）：调小「轮盘大小」或「菜单距离」，或换更大的显示器。
   如果要求"任何情况下都不裁切"，需要允许画布突破工作区上限 —— 那与决策四冲突，
   故未自行决定。
2. **0.5px 容差**：二分判据用 `canvas ≤ limit + 0.5`（浮点安全余量）。
   实测所有档位均为 `canvas ≤ limit`，余量未被用到；但这是实现细节，记录在此。
3. **`bandPaddingDp` / `rimLobeDp` 不参与压缩**（见 §6 末）。
4. **DPI / 显示器变化**的检测是"下次重建时按新工作区算"，探针没有常驻
   显示器监听器；切屏后点一次桌宠打开菜单（会走 stale 重建）即生效。

### 真机验收步骤（新产物）

1. 运行 `build_incrB2\windows\x64\runner\Release\petlife.exe`；
2. 打开控制面板 → 「桌宠轮盘」：确认「轮盘大小」行同时显示用户值与
   「当前屏幕实际显示 xx%」；把轮盘大小拉到 250%，在 1920×1040 上应显示
   **169%** + 「原因：受当前显示器可用空间限制」；
3. 回到桌宠，观察窗口矩形：改动轮盘设置会让窗口变一次大小（这是决策允许的
   **一次原子重建**，且桌宠不会跳位）；
4. 反复点击桌宠开 / 关轮盘、进入子菜单 / 返回：窗口矩形必须**一动不动**；
5. 打开设置页的「轮盘菜单诊断」面板，核对 `canvasRebuildCount` /
   `canvasAnchorErrorPx`（应 ≤ 1）/ `effectiveWheelScale` / `canvasCompressed`；
6. 进入控制面板再返回桌宠：画布应按**当前设置**恢复（不是默认档）。

# 05 · 数据库设计与迁移

> 引擎：**SQLite（WAL 模式）**，通过 `sqflite_common_ffi` + `sqlite3_flutter_libs` 直连。
> Schema 版本：**3**（`AppConstants.databaseSchemaVersion`）。
> - **v1**（阶段 0）：素材 / 角色 / 作品包 / 状态映射 / 本地设置，以及预留的 `activity_segments`
> - **v2**（阶段 1）：`applications` / `activity_checkpoints` / `daily_usage` / `tracking_settings`
> - **v3**（Phase 2）：`account_session_state` / `sync_state` / `sync_outbox` —— **已实施**，见 §8
>
> 位置：`<AppData>/PetLife/petlife.db`。
>
> ⚠️ **这是客户端本地库**。Phase 2 的服务端使用**另一套完全独立的库**
> （PostgreSQL 16，7 张表：`users` / `devices` / `refresh_tokens` / `activity_segments` /
> `daily_usage` / `user_applications` / `sync_log`），由 Alembic 管理，
> 详见 `15-Phase2总体架构.md` §3 与 `16-服务端部署与配置.md`。

## 2.1 v2 迁移说明

v2 的全部语句都在 `DbSchema.v2Statements`，并且**同时**被用于两条路径：

- `createStatements`（新库直接建全量）= `v1Statements + v2Statements`；
- `migrations[2]`（v1 老库升级）= `v2Statements`。

因为每条语句都带 `IF NOT EXISTS`，同一份语句既可用于新建也可用于升级，**不会重复执行出错**。

**对阶段 0 数据的保证**：

- v2 **只新增表与索引**，没有任何 `DROP` / `ALTER` / `UPDATE`；
- `activity_segments` 在 v1 已建好，阶段 1 直接写入，不需要改结构；
- 因此升级后作品包 / 角色 / 素材 / 状态映射 / 本地设置**逐字段不变**。

这一点由 `test/activity_migration_test.dart` 用**真实数据库**验证：
手工建一个 v1 库 → 写入 1 个作品包、1 个角色、2 个素材、1 条映射、3 条设置 →
用 v2 打开 → 断言 `user_version = 2`、新表存在、且上述数据的每个关键字段都还在。
同一个测试还验证了「重复打开幂等」与「新库全量建表结果与升级路径一致」。

## 2.2 v3 迁移说明

v3 全部语句在 `DbSchema.v3Statements`，同样是 `createStatements` 与 `migrations[3]` **共用同一份**，
每条都带 `IF NOT EXISTS`，因此新建库与升级库不会漂移。

**对 v1 / v2 数据的保证**：

- v3 **只新增 3 张表 + 3 个索引**，没有任何 `DROP` / `ALTER` / `UPDATE`；
- 升级路径为 `for (v = from + 1; v <= to; v++)`，v2 库升级时**只执行 `migrations[3]`**，
  v1 库则依次执行 `migrations[2]`、`migrations[3]`；
- 因此升级后作品包 / 角色 / 素材 / 状态映射 / 本地设置 / 应用库 / 活动段 / 每日用量**逐字段不变**。

测试 `test/sync_migration_v3_test.dart`（6 项）用**真实数据库**验证：

| 用例 | 断言 |
|---|---|
| v2 → v3 升级 | `user_version = 3`，3 张新表存在，且 v2 写入的素材 / 设置 / 活动段 / 每日用量逐字段仍在 |
| 新库直接建 v3 | 全量 `createStatements` 结果与升级路径一致 |
| 重复打开 | 第二次 `open()` 不再执行迁移，数据不变 |
| 新表读写 | 三张表都能正常 insert / select / update |
| **无敏感列** | `PRAGMA table_info(account_session_state)` 中**不存在** `password` / `token` 类列名（黑名单断言） |
| **部分唯一索引生效** | 同一 `(entity_type, entity_key)` 在 `acknowledged_at IS NULL` 时插入第二条会抛 `UNIQUE` 约束错误 |

## 3. 设计原则

1. **所有业务表都带 `owner_id`**。阶段 0 只有一个本地用户 `local.default`，但表结构、索引、唯一约束都已按多用户设计，服务端接入时**无需改表**。
2. **时间统一存毫秒时间戳（INTEGER）**，避免时区与字符串格式歧义。
3. **布尔存 0/1（INTEGER）**。
4. **托管路径与原始路径分开存**：`file_path` 是托管副本，`original_file_path` 是用户原始位置。删除素材只删托管副本。
5. **外键 + `ON DELETE CASCADE`**：删作品包会连带删角色，删角色会连带删素材与映射，不会留下孤儿行。
6. **唯一约束表达业务语义**：`UNIQUE(owner_id, name)` 保证同用户下作品包不重名；`UNIQUE(pack_id, internal_name)` 保证同包内角色不重名；`UNIQUE(character_id, emotion_name, variant_name)` 保证同一角色的同名同变体只有一条——这正是**重复导入幂等**的落点。

## 5. WAL 与并发

启用 WAL 的好处：读写不互相阻塞，桌宠渲染线程读素材元数据时不会因为后台导入写库而卡顿；写入是追加式的，崩溃后恢复更可靠。

代价是会出现 `petlife.db-wal` 与 `petlife.db-shm` 两个伴随文件（**这两个文件不是残留垃圾，不要手动删除**；正常关闭时 SQLite 会做检查点）。

## 6. 迁移机制

`DbSchema.migrations` 是 `Map<int, List<String>>`：**版本号 → 升级语句列表**。
`AppDatabase.open()` 会比对 `PRAGMA user_version` 与目标版本，逐级执行缺失的迁移：

```dart
for (int v = from + 1; v <= to; v++) { ... }
```

当前状态：

| 版本 | 内容 | 是否已实现 |
|---|---|---|
| v1 | 阶段 0 的 6 张表（`DbSchema.v1Statements`） | 阶段 0 |
| v2 | 阶段 1 新增 4 张表 + 4 个索引（`DbSchema.v2Statements`，`migrations[2]`） | 阶段 1 |
| v3 | Phase 2 新增 3 张表 + 3 个索引（`DbSchema.v3Statements`，`migrations[3]`） | **Phase 2（已实施）** |

`createStatements`（新库）= `v1Statements + v2Statements + v3Statements`；`migrations = {2: v2Statements, 3: v3Statements}`。
两份路径共用同一批语句，且全部带 `IF NOT EXISTS`，因此**全新安装与升级安装不会出现两条不一致的建表路径**，重复执行也不会报错。

后续阶段新增表 / 字段的流程：

1. 在 `DbSchema.v3Statements` 之后再追加一份 `v4Statements`，`migrations` 里加 `4: v4Statements`；
2. 把 `AppConstants.databaseSchemaVersion` 提升为 `4`；
3. **必须**补一条真实数据库迁移测试（照抄 `test/sync_migration_v3_test.dart` 的写法：
   建旧版库 → 写旧版数据 → 用新版本打开 → 断言旧数据逐字段未变）。

### 6.1 `v1Statements` 为什么是公开的

迁移测试需要**真的重建一个 v1 老库**才能验证升级路径。把 `v1Statements` 公开
（而不是复制一份到测试里）保证了「测试用的老库结构 = 真实历史结构」，
不会因为测试里手抄的建表语句与真实语句漂移而出现假通过。

## 8. v3（Phase 2 客户端）—— 已实施

> ✅ 本节描述的是**当前状态**。`AppConstants.databaseSchemaVersion = 3`，
> 迁移语句在 `lib/database/schema.dart` 的 `DbSchema.v3Statements`。

三张表**只新增、不改动任何既有表**，既有素材、设置与使用记录零丢失（见 §2.2 的测试证据）。
表名常量：`DbSchema.tableAccountSession` / `tableSyncState` / `tableSyncOutbox`。

### 8.1 `account_session_state`

**单行表**（`CHECK (id = 1)`），只保存**非敏感**账户信息与一个凭据引用；
**没有任何令牌或密码列**（该断言由 `sync_migration_v3_test.dart` 用 `PRAGMA table_info` 机器校验）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 固定 `1`（本地同一时刻只有一个当前账户） |
| `server_base_url` | TEXT NOT NULL | 服务端地址，用户可改 |
| `user_id` | TEXT NOT NULL | 服务端账户 UUID |
| `email` | TEXT NOT NULL | 便于离线展示与预填 |
| `display_name` | TEXT | 可空 |
| `device_server_id` | TEXT | 服务端设备 UUID（设备注册成功后写入） |
| `credential_reference` | TEXT NOT NULL | **凭据存储里的条目名**，例如 `PetLife:account`；令牌本体在 Credential Manager / DPAPI，不在这里 |
| `access_token_expires_at` | INTEGER | 仅用于"是否该提前刷新"的判断，不是凭据本身 |
| `updated_at` | INTEGER NOT NULL | 毫秒时间戳 |

DAO：`lib/database/dao/account_session_dao.dart`（`load()` / `save()` / `clear()`）。

### 8.3 `sync_outbox`

待上传队列。**本地采集先写业务表，再在同一个业务流程里写 outbox**，
上传成功后由服务端确认才置 `acknowledged_at`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | **稳定 UUID**（`Ids.*` 生成），远程身份只用它，不用 SQLite 自增 ID |
| `entity_type` | TEXT NOT NULL | 三类之一 |
| `entity_key` | TEXT NOT NULL | 业务键：活动段 = `segment.id`；每日用量 = `<device_local_id>:<day_key>`；应用 = `app_key` |
| `entity_local_id` | TEXT | 便于回查本地行（可空） |
| `operation` | TEXT NOT NULL DEFAULT 'upsert' | 目前只有 upsert（快照覆盖语义） |
| `payload_json` | TEXT NOT NULL | **推送时重建**的完整快照（见 §8.6） |
| `created_at` | INTEGER NOT NULL | |
| `attempt_count` | INTEGER NOT NULL DEFAULT 0 | 失败次数，驱动退避 |
| `next_attempt_at` | INTEGER NOT NULL DEFAULT 0 | 到期前不重试 |
| `last_error` | TEXT | 最近错误（已脱敏） |
| `acknowledged_at` | INTEGER | **只有收到服务端确认才置位**；为空表示仍需重试 |

索引：

```sql
CREATE INDEX idx_sync_outbox_pending ON sync_outbox (acknowledged_at, next_attempt_at, created_at);
CREATE INDEX idx_sync_outbox_entity  ON sync_outbox (entity_type, entity_key);
CREATE UNIQUE INDEX uq_sync_outbox_pending_entity
    ON sync_outbox (entity_type, entity_key) WHERE acknowledged_at IS NULL;
```

**关键设计：那是一个 `WHERE acknowledged_at IS NULL` 的"部分唯一索引"。**
它把"同一实体最多只允许一条未确认记录"这条业务规则**下沉到数据库层**，
因此重复排队不可能产生重复数据 —— 不依赖应用层"记得先查询再插入"。
已确认的历史行不受约束（保留审计痕迹），符合用户要求里"重复排队和重复确认必须幂等"。

入队时若已存在未确认行，采用 **`ON CONFLICT ... DO UPDATE` 刷新 payload / created_at，
但保留 `attempt_count` 与 `next_attempt_at`** —— 否则每次重新入队都会把退避重置，
失败记录会变成"忙等重试"。

DAO：`lib/database/dao/sync_outbox_dao.dart`（`enqueue()` / `enqueueAll()`（同一事务）/ `pending()` / `acknowledge()` / `markFailed()` / `pendingCounts()` / `purgeAcknowledged()`）。

### 8.4 令牌存储方案（已落地）

实际实现与本文 §8.4 早先的"计划"一致，优先级：

1. **Windows Credential Manager**（首选）：`CredWriteW` / `CredReadW` / `CredDeleteW`，
   走 Dart FFI（`lib/sync/win32_credential_native.dart`，`CREDENTIALW` 按 x64 布局声明）；
2. **不可用时退化为 DPAPI 文件后端**：`CryptProtectData` / `CryptUnprotectData`，
   **用户范围（`CRYPTPROTECT_UI_FORBIDDEN`，不加 `LOCAL_MACHINE`）**，
   因此密文只能被同一个 Windows 用户解开；密文保存在
   `<AppData>/PetLife/credentials/<条目名>.bin`；
3. 两者都不可用时用 `InMemoryCredentialStore`（**仅用于测试与降级诊断**，重启即丢）。

启动时由 `lib/sync/credential_store_factory.dart` 用**探针式探测**决定后端：
写入一个探针条目 → 读回 → 比对 → 删除，三步都成功才采用该后端；
探测失败**不是静默回退**，后端名会显示在账户页与诊断页（`sync_credential_backend`）。

SQLite 中**绝不明文保存密码**（客户端根本不保存密码），也**不保存任何令牌**。
真实联调中该后端被识别为 `Windows Credential Manager`。

### 8.5 与服务端主键的对接

客户端现有的键已经**天然对齐**服务端约定，因此 v3 不需要改任何既有表：

| 客户端 | 服务端 |
|---|---|
| `activity_segments.id`（`Ids.segment()` 生成的确定性 UUID） | `activity_segments.(user_id, id)` |
| `daily_usage.(owner_id, device_local_id, day_key)` | `daily_usage.(user_id, device_id, local_day)` |
| `applications.app_key`（规范化可执行文件名） | `user_applications.(user_id, app_key)` |
| `activity_segments.sync_status`（v1 起预留） | 由 outbox 的 `acknowledged_at` 取代（该列保留，不再作为同步依据） |

> ⚠️ 联调发现的真实约束：服务端的 `ActivitySegmentIn.id` 是 `uuid.UUID`，
> **不能**用 `e2e-segment-1` 这类字符串，否则服务端返回 422。客户端生成的确定性 UUID 天然满足。

### 8.6 payload 是"推送时重建"，不是"入队时冻结"

`sync_outbox.payload_json` 在入队时写入一份，但 `OutboxProducer.buildPayload()` 在**真正推送时**
会按 `entity_key` 回查本地业务表**重新构造**payload。这样做的好处：

- `daily_usage` 永远上传**当前完整快照**，天然满足"不做增量累加"的要求；
- 本地行的后续修正会自动反映到下一次上传，不需要"再排一次队"；
- 活动段的 `updated_at` 取自 `ended_at`（进行中的段取"现在"），不会因为段还在跑而被服务端当成已完成。

代价是 outbox 的 `payload_json` 不再是"唯一真相"，这一点在 `18-数据同步协议.md` 中有说明。

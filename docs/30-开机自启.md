# 30 - 开机自启（Windows）

> 范围：Windows。Android 没有"登录后自动启动"的等价机制，该选项在 Android 上**隐藏**。
>
> **更正（2026-10-05）**：本行"Android 没有等价机制"的说法**已过时、被取代**。
> Android 侧自 Phase 4D 起已实现开机自启——设置键 `overlay.autostart_enabled`、
> 接收器 `BootCompletedReceiver`，结果在设置页以"最近一次开机结果"呈现，详见 **§8**。
> 本文件 §1~§7 的 Windows 注册表方案不受影响。

## 1. 一句话设计

设置页的「开机自动启动」不是"把这个偏好存进数据库"那么简单，它同时维护**两个真相**：

| | 存在哪 | 谁是权威 | 谁写它 |
|---|---|---|---|
| 用户**意图** | SQLite `local_settings.behavior.launchAtStartup` | 用户操作 | `SettingsController` |
| 系统**实况** | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的 `PetLife` 值 | **系统** | `WindowsStartupRegistrar` |

由此推出三条行为：

1. **开关渲染的是系统实况**，不是数据库里的意图。用户在 `regedit` 或
   任务管理器里手工删掉启动项后，界面会如实显示"关闭"——
   否则数据库里那个 `true` 就是在撒谎。
2. **启动时按意图修复实况**：偏好为开启时，每次启动都会用**当前 exe 的路径**
   重写一遍启动项。于是把整个发布目录搬到别处（或重命名）之后，
   下次启动就会自动把路径修正过来。
3. **失败必须显式**：注册表写失败时不写偏好、抛异常，设置页把开关回滚到真实状态
   并把原因显示在开关下面（需求明确禁止"假装成功"）。

## 2. 注册表细节

```
键  ：HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
值名：PetLife
类型：REG_SZ
数据："C:\Program Files\PetLife\petlife.exe"
```

* 用 **HKCU 而不是 HKLM**：不需要管理员权限，也只影响当前登录用户；
* 值名固定 `PetLife`，在「任务管理器 → 启动应用」里一眼可辨；
* **启动命令始终加双引号**：路径含空格时 Windows 会按第一个空格切分命令行，
  不加引号会启动失败（例如 `C:\Program Files\...`）；无空格时加引号也完全合法，
  所以统一加，避免"有的机器行有的机器不行"；
* 命令指向的是**当前正在运行的 `petlife.exe` 的完整绝对路径**
  （`Platform.resolvedExecutable`），也就是完整发布目录里的那个 exe
  ——不是复制到别处的一个副本，因为 `data/`、`sqlite3.dll` 等都在它旁边；
* 相对路径会被**拒绝**并给出明确原因：写进 `Run` 项的相对路径在登录时
  工作目录不确定，会造成"注册成功但启动不了"。

FFI 用的是 `RegSetKeyValueW` / `RegDeleteKeyValueW` / `RegGetValueW`（advapi32），
可以直接用预定义句柄 `HKEY_CURRENT_USER` 操作，不必成对管理
`RegOpenKeyEx` / `RegCloseKey`，减少句柄泄漏面。手写绑定而非引入 `win32` 包，
是为了与本工程既有做法（`win32_credential_native.dart` / `win32_process_stats.dart` /
`winhttp_system_proxy.dart`）保持一致。

## 3. 代码结构

| 文件 | 职责 |
|---|---|
| `lib/platform/startup_registrar.dart` | 中立接口 `StartupRegistrar` + `StartupRegistrationException` + `UnsupportedStartupRegistrar` |
| `lib/platform/windows/windows_startup_registrar.dart` | Windows 实现（FFI 读写注册表、`buildCommand` 引号处理） |
| `lib/settings/startup_registration_service.dart` | 协调器：系统实况为准、失败回滚、启动对齐、`ChangeNotifier` |
| `lib/ui/pages/settings_page.dart` | `StartupSwitchTile`（开关 + 错误提示 + 失败回滚） |
| `lib/app/app_scope.dart` | 装配 + 启动时调用 `reconcileOnStartup()` |

平台边界：

* `StartupRegistrar` 是**能力接口**，Android 对应的
  `AndroidPlatformServices.startupRegistrar` 返回 `UnsupportedStartupRegistrar`；
* `PlatformCapabilities.supportsLaunchAtStartup` 在 Windows 为 `true`、Android 为 `false`，
  设置页据此**整个分区不渲染**（不是显示一个点了会报错的开关）；
* `test/platform_isolation_test.dart` 把 `windows_startup_registrar.dart` 列入
  "桌面专属实现"清单：它只允许出现在 `lib/platform/windows/**`，
  Android 编译单元出现即判定失败。

## 4. 行为矩阵

| 场景 | 系统注册表 | 数据库意图 | 界面开关 |
|---|---|---|---|
| 用户打开开关（成功） | 写入 `PetLife` | `true` | 开 |
| 用户关闭开关（成功） | 删除 `PetLife` | `false` | 关 |
| 用户打开开关（**注册表写失败**） | 不变 | **不变（仍 false）** | 关 + 显示失败原因 |
| 用户关闭开关（删除失败） | 不变（仍有） | **不变（仍 true）** | 开 + 显示失败原因 |
| 启动时意图=`true` | 按当前 exe 重写 | `true` | 开 |
| 启动时意图=`true` 但注册失败 | 不变 | **被校正为 `false`** | 关 |
| 启动时意图=`false` 但系统里有条目 | 不变（不删） | **被校正为 `true`** | 开 |
| 「恢复默认设置」 | 删除 `PetLife` | 重置为默认（`false`） | 关 |
| 「恢复默认设置」但删除失败 | 不变（仍有） | 重置为默认 | 开 + 弹窗提示未清理 |
| 用户在 regedit 里手工删除启动项 | 无 | 不变 | 关（下次启动会把意图校正为 `false`） |

## 7. 已知限制

* **只在登录时启动，不注册任何计划任务/服务**：符合"普通桌宠应用"的定位，
  也不需要管理员权限；
* **不提供"以管理员身份启动"**：`Run` 项做不到提权启动，
  需要提权的场景不在本功能范围内；
* **删除失败时不会自动重试**：界面会显示错误，用户可再点一次关闭开关重试；
* ~~**Android 无此能力**~~：**该结论已过时，见 §8**。本文 §1~§7 描述的 Windows
  注册表方案保持不变；Android 侧自 Phase 4D 起通过 `BOOT_COMPLETED` 接收器
  实现了"开机自启"，但它是**另一套机制**（不写注册表、不用
  `StartupRegistrar`），因此没有违反本文前面的任何设计。

## 8. Android 开机自启（Phase 4D）

> 与 Windows 方案**互相独立**：Windows 写 `HKCU\...\Run`；Android 用
> `RECEIVE_BOOT_COMPLETED` + 前台服务。两者的开关、持久化位置、失败口径都不同。

### 8.1 语义（与"显示桌宠"分开）

| 设置 | 存在哪 | 含义 |
|---|---|---|
| 开机自动启动 | 原生 `SharedPreferences`（`petlife_overlay` 的 `overlay.autostart_enabled`） | **只**决定"重启后要不要把服务拉起来" |
| 显示 / 隐藏桌宠 | 同一份 `SharedPreferences` 的 `overlay.enabled` / `overlay.hidden` | 当前桌宠在不在显示 |

三条不变量：

1. 关闭自启后重启 → **什么都不启动**；
2. 用户在重启前把桌宠**隐藏**了 → 仍按**隐藏**方式启动（`START_HIDDEN`），
   与"关闭自启"是两回事，绝不把用户藏起来的东西重新弹出来；
3. 开关**写透**到原生 SharedPreferences —— 开机广播到达时 Flutter 还没启动，
   `BOOT_COMPLETED` 接收器必须在**不依赖 Flutter** 的情况下读到它。

### 8.2 代码结构

| 文件 | 职责 |
|---|---|
| `.../overlay/BootAutostart.kt` | 纯决策 `decide` + 注入式执行 `run`（JVM 可测）；`BootStore` 抽象 |
| `.../overlay/BootCompletedReceiver.kt` | 接收 `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`，读标志 → 决策 → 启动 |
| `.../overlay/PetOverlayStore.kt` | 新增 `autostartEnabled` / `bootResult*` 键 |
| `.../overlay/OverlayActions.kt` | 新增 `START_HIDDEN` 指令与 `EXTRA_TRIGGER=boot` |
| `.../overlay/PetOverlayService.kt` | 与界面**共用**同一个入口；启动成功后回填 `started` |
| `lib/ui/widgets/overlay_pet_card.dart` | 开关 + "最近一次开机结果" + **按需**的厂商限制引导 |

### 8.3 与 targetSdk 相关的系统限制（本项目的遵从方式）

* **Android 12+（API 31）**：后台启动前台服务默认被禁，但"接收
  `BOOT_COMPLETED` / `ACTION_MY_PACKAGE_REPLACED` 的接收器"是官方**豁免**；
* **Android 14+（API 34）**：必须声明前台服务类型 + 对应权限 —— 本项目为
  `specialUse` + `FOREGROUND_SERVICE_SPECIAL_USE`（首版就有）；
* **Android 15+（API 35）**：`BOOT_COMPLETED` 接收器**不允许**启动
  `dataSync` / `camera` / `location` 等类型；本项目用 `specialUse`，不在禁止之列；
  另外 `SYSTEM_ALERT_WINDOW` 的"广泛豁免"被收窄，但 `BOOT_COMPLETED` 本身
  仍是独立豁免；
* 仍以 `try/catch` 兜底：系统若拒绝启动，记 `system_blocked` 并**不重试**。

### 8.4 解锁与存储

接收器 `directBootAware=false`（默认），**不**处理 `LOCKED_BOOT_COMPLETED`：
自启标志存在凭据加密存储里，设备未解锁时读不到，因此未解锁前不做任何事 ——
这正好满足"不要在用户解锁前把悬浮窗准备好"。

### 8.5 开机结果

接收器写 `start_requested`（或 `missing_overlay_permission` / `disabled` /
`system_blocked` / `already_running` / `duplicate_ignored`）；服务真正起来后由
`PetOverlayService` 回填 `started` / `start_failed`。设置页把结果码翻译成一句话
（已启用 / 最近一次启动成功 / 缺少悬浮窗权限 / 系统限制后台启动 /
需要用户打开应用完成恢复…），并只在真的失败时才给出**按需**的厂商后台限制引导。

### 8.6 自动化测试

`android/app/src/test/kotlin/.../BootAutostartTest.kt`（16 项）：关闭→不启动、
开启→恰好一次、隐藏→隐藏启动、重复信号去重（服务已运行 / 时间窗）、

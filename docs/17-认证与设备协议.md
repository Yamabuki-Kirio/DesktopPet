# 17 · 认证与设备协议

> 服务端实现见 `server/app/security/`、`server/app/services/auth_service.py`、
> `server/app/services/device_service.py`。

## 1. 令牌模型

| | Access Token | Refresh Token |
|---|---|---|
| 形态 | JWT（HS256，自包含） | 不透明随机串（`secrets.token_urlsafe(48)`） |
| 有效期 | 15 分钟（可配） | 30 天（可配） |
| 服务端是否存储 | ❌ 不存 | ✅ 只存 `sha256` 哈希 |
| 是否轮换 | 不需要 | **每次刷新都换新**，旧的立刻失效 |
| 传递方式 | `Authorization: Bearer <token>` | 请求体 `refresh_token` |

Access Token 载荷：

```json
{
  "sub": "<user uuid>",
  "typ": "access",
  "iat": 1790512351,
  "exp": 1790513251,
  "iss": "petlife",
  "jti": "<random hex>",
  "dev": "<device uuid，可选>"
}
```

`typ` 用于防止把 Refresh Token 当 Access Token 使用（有测试断言）。

## 2. 为什么 Refresh Token 不用 JWT

需求要求「修改密码、删除账户、注销全部会话后，旧 Refresh Token 全部失效」。
JWT 是自包含的，服务端无法"撤回"一个已签发的 JWT——只能等它自然过期，
或者引入黑名单（那本质上又回到了服务端状态）。因此这里用**不透明随机串 +
服务端存哈希**，让吊销成为一次数据库更新，立即生效。

## 3. 刷新与轮换（含泄露检测）

```
客户端                        服务端
  │  POST /auth/refresh {refresh_token: R1}
  ├───────────────────────────►│ 查 sha256(R1)
  │                            │ 未撤销、未过期 → 签发 A2 + R2，并把 R1 标记
  │                            │ revoked_at=now, replaced_by_id=<R2.id>
  │◄───────────────────────────┤ {access_token: A2, refresh_token: R2}
  │  ... 若 R1 被再次使用 ...    │
  ├───────────────────────────►│ R1 已撤销**且** replaced_by_id 非空
  │                            │ → 判定为泄露：吊销该用户**全部** refresh token
  │◄───────────────────────────┤ 401 refresh_token_reused
```

**为什么区分两种"已撤销"**：

- `replaced_by_id` 非空 → 这是被轮换掉的旧令牌，再次出现说明**有人拿到了旧令牌**
  → 全量吊销（宁可打断所有设备，也不放任疑似泄露的会话继续用）；
- 没有 `replaced_by_id`（因为注销 / 改密 / 撤销设备被吊销）→ 只回 `token_invalid`。
  否则一个在途的重试请求会把用户所有设备一起踢下线，体验极差。

## 4. 接口清单

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/api/v1/auth/register` | — | 注册；返回令牌（等价自动登录）。可选带 `device` 直接绑定 |
| POST | `/api/v1/auth/login` | — | 登录。可选带 `device` 直接绑定 |
| POST | `/api/v1/auth/refresh` | — | 刷新 + 轮换；可带 `device_local_id` 补绑定设备 |
| POST | `/api/v1/auth/logout` | — | 注销当前会话（传 `refresh_token`，或带 `X-Device-Id` 注销该设备全部） |
| POST | `/api/v1/auth/logout-all` | ✅ | 注销该账户全部会话 |
| GET | `/api/v1/me` | ✅ | 当前账户 |
| PATCH | `/api/v1/me` | ✅ | 修改显示名称 |
| POST | `/api/v1/me/password` | ✅ | 修改密码 → **吊销全部会话** |
| DELETE | `/api/v1/me` | ✅ | 删除账户（需当前密码） |

### 4.1 注册

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "email": "alice@example.com",
  "password": "至少8位",
  "display_name": "Alice",
  "device": {
    "device_local_id": "a9f0...-uuid",
    "device_name": "我的台式机",
    "platform": "windows",
    "architecture": "x64",
    "os_version": "Windows 11 23H2",
    "app_version": "0.2.0"
  }
}
```

响应 `201`：

```json
{
  "access_token": "eyJ...",
  "token_type": "bearer",
  "expires_in": 900,
  "refresh_token": "kJ3....",
  "refresh_expires_at": "2026-10-27T12:00:00Z",
  "user": {
    "id": "...", "email": "alice@example.com", "display_name": "Alice",
    "status": "active",
    "created_at": "2026-09-27T12:00:00Z", "updated_at": "2026-09-27T12:00:00Z"
  },
  "device_id": "b7c1...-uuid"
}
```

`device` 是**可选**的。带上它的好处：令牌会绑定到该设备，
撤销设备时这台机器的 Refresh Token 会立刻失效。

### 4.2 登录不泄露邮箱是否已注册

`邮箱不存在` 与 `密码错误` 返回**相同**的状态码、错误码与文案：

```json
{"error": {"code": "invalid_credentials", "message": "邮箱或密码错误", "request_id": "..."}}
```

只有密码正确但账户被停用时才返回 `account_disabled`（不会泄露邮箱是否存在）。

### 4.3 修改密码

```http
POST /api/v1/me/password
{"current_password": "...", "new_password": "..."}
```

成功后：`revoked_sessions` 数量 > 0，**所有** Refresh Token 失效，
旧密码立即不能登录，新密码可以。响应提示客户端重新登录。

### 4.4 删除账户

```http
DELETE /api/v1/me
{"current_password": "...", "new_password": "some-placeholder"}
```

> 复用 `UpdatePasswordRequest` 模型只是为了复用「需要密码确认」的字段，
> 语义上是「当前密码」校验。

行为：

1. 吊销全部 Refresh Token；
2. **物理删除**该用户的设备（级联删除其活动段与每日用量）；
3. 账户置为 `deleted` + `deleted_at`；
4. 邮箱改为 `local+deleted.<随机>@domain`，**释放原邮箱**（可重新注册）；
5. 密码哈希替换为随机值（旧密码彻底不可用）。

删除后：无法登录、旧 Access Token 立即被拒（`get_current_user` 检查 `status`）、
无法再访问任何数据。

## 5. 设备系统

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/devices/register` | 注册或更新设备（幂等，按 `device_local_id`） |
| GET | `/api/v1/devices` | 列出该账户全部设备（含已撤销），当前设备标记 `is_current` |
| GET | `/api/v1/devices/{id}` | 单个设备 |
| PATCH | `/api/v1/devices/{id}` | 修改 `device_name` / `model_name` |
| DELETE | `/api/v1/devices/{id}` | **撤销**设备 |

### 5.1 设备标识与隐私

- `device_local_id` 由**客户端本地生成的 UUID**，重启不变；
- 服务端**不采集**硬件序列号、MAC 地址或其他难以撤销的硬件指纹；
- 服务端只保存客户端自报的：名称、平台、架构、OS 版本、App 版本、型号备注；
- `model_name` 是用户备注，客户端上报**只在为空时填充**，不覆盖用户已填的值。

### 5.2 撤销设备做了什么

```
DELETE /api/v1/devices/{id}
  1. revoked_at = now
  2. 吊销该设备关联的全部 Refresh Token（revoked_sessions > 0）
  3. device_local_id 改名加上墓碑后缀 "#revoked:<8位>"
```

第 3 步是关键：**释放原来的 `device_local_id`**。否则用户在重装/重新登录后
会被 `UNIQUE(user_id, device_local_id)` 永久挡住，无法重新绑定同一台机器。
改名保留了审计痕迹（旧行还在）。

### 5.3 撤销后如何被拦住（两条防线）

1. **`X-Device-Id` 校验**：`GET/POST /sync/*` 都要求该请求头，
   `revoked_at` 非空直接返回 `403 device_revoked`；
2. **令牌吊销**：该设备的 Refresh Token 已失效，刷新会拿到
   `token_invalid` / `device_revoked`。

撤销设备是幂等的（重复撤销返回 `revoked_sessions: 0`，不报错）。

## 6. 统一错误格式

所有 4xx / 5xx 都是这一个结构：

```json
{
  "error": {
    "code": "device_revoked",
    "message": "该设备已被撤销，请重新登录或联系支持",
    "request_id": "8f2c1d9e4b7a4c0e9f3b1a2d5c6e7f80",
    "detail": null
  }
}
```

响应头同时带 `X-Request-Id`，与服务端日志对齐（排查问题时只需要用户提供这个 id）。
若客户端自己传了 `X-Request-Id`，服务端会沿用它。

### 6.1 错误码

| code | HTTP | 客户端应做什么 |
|---|---|---|
| `invalid_credentials` | 401 | 提示账号或密码错误 |
| `email_taken` | 409 | 提示换邮箱 |
| `unauthorized` | 401 | 重新登录 |
| `token_expired` | 401 | **静默刷新**后重试一次 |
| `token_invalid` | 401 | 重新登录 |
| `refresh_token_reused` | 401 | 重新登录（并提示"检测到异常"） |
| `account_disabled` | 403 | 提示账户被停用 |
| `device_not_found` | 404 | 重新注册设备 |
| `device_revoked` | 403 | 停止同步 + 提示重新登录 |
| `validation_error` | 422 | 客户端 bug，记录日志 |
| `invalid_uuid` | 422 | 客户端 bug |
| `invalid_time_range` | — | 出现在 `push` 的 `rejected[]` 里 |
| `batch_too_large` | 413 | 拆小批次 |
| `conflict` | 409 | 重试该条 |
| `internal_error` | 500 | 指数退避重试，带上 `request_id` 反馈 |

**校验错误不回显输入值**：`validation_error` 的 `detail` 只含字段路径与原因，
不会把用户提交的原文（可能含密码）回显出来（有测试断言）。

## 7. 时间约定

- 服务端内部与数据库一律 **UTC**；
- API 返回的 ISO 8601 时间一律带 `Z` 后缀（如 `2026-09-27T12:00:00Z`）；
- 请求里的时间同时接受 ISO 8601 字符串与 epoch（秒或毫秒，`>= 1e11` 视为毫秒）；
- 「今天」的边界由客户端的 `tz_offset_minutes` 决定，**绝不用服务器本地时区**。

## 2. 技术选型

| 层面 | 选型 | 说明 |
|---|---|---|
| UI / 逻辑 | **Flutter 3.47.5 stable / Dart 3.13.4** | 一套代码后续可复用到 Android（阶段 4） |
| 目标平台 | **Windows x64**（MSVC 14.44 + Windows SDK 10.0.26100） | 只构建 Windows |
| 持久化 | **SQLite（WAL）**，`sqflite_common_ffi` + `sqlite3_flutter_libs` | 桌面端走 FFI，不依赖平台插件通道 |
| 窗口 / 托盘 / 多屏 | `window_manager` / `tray_manager` / `screen_retriever` | 均为官方生态插件 |
| Windows 原生能力 | **Dart FFI 直连 Win32**（`kernel32.dll` / `psapi.dll`） | 见 §5 决策 B |
| 图片解码 | Flutter 自带 Skia WebP 解码器 + 自研 RIFF 容器解析 | 见 `02-素材规范与导入校验.md` |

依赖清单见 `pubspec.yaml`。其中 `hooks.user_defines.sqlite3` 段是**必需**的，原因见 `06-构建运行手册与开发环境.md` §4。

## 3. 启动装配顺序

单一入口 `lib/main.dart`，整个装配过程由 `AppServices.bootstrap()`（`lib/app/app_scope.dart`）负责。顺序是**强依赖顺序**，不可调换：

```
main()
 ├─ SingleInstanceGuard.tryAcquire()   ⓪ 命名互斥体（重复启动直接 exit(0)）
 └─ runZonedGuarded                    ① 先装全局错误兜底（ErrorHandler.install）
     └─ AppServices.bootstrap()
         ├─ 1. AppPaths.initialize()       创建 AppData 目录树
         ├─ 2. AppLog.initialize()         日志落盘
         ├─ 3. AppDatabase.open()          SQLite 打开 + 建表 + 迁移（v1→v2）+ WAL
         ├─ 4. SqliteCharacterRepository   仓储层
         │     SqliteSettingsRepository
         ├─ 5. AssetValidator / AssetDecoder
         ├─ 6. DefaultAssetImporter / ZipAssetImporter
         ├─ 7. SettingsController.load()   读回上次配置
         ├─ 8. WindowsWindowController.initialize()   窗口 + 多屏拓扑
         ├─ 9. PetFrameController / DefaultStateEngine / PetPresenter
         ├─ 9.5 阶段 1：ApplicationRepository.load()
         │      ActivitySegmentService / ActivityTracker / UsageAnalyticsService
         │      TrackingSettingsDao.load()
         ├─ 10. TrayService                托盘（回调挂到 window/panel/stats/tracking/exit）
         └─ 11. PerfSampler                性能采样器（等待 UI 启动）
     └─ runApp(PetLifeApp)
         └─ AppShell
             ├─ initializeTray()           真正注册托盘图标
             ├─ 恢复上次角色/表情             （验收第 18 项）
             ├─ presenter.start()          启动渲染
             ├─ 切换到「桌宠模式」
             └─ startActivityTracking()    启动活动采集（须在角色绑定之后）
```

任一步抛出异常 → `ErrorHandler.record('bootstrap', ...)` → 退化为**启动失败兜底页**（显示错误原文 + 日志路径 + 常见原因），而不是白屏或静默退出。

## 5. 关键设计决策（以及为什么）

### 决策 A：桌宠与控制面板是**同一个窗口的两种形态**，不是两个原生窗口

`AppShell` 持有 `WindowMode.pet` / `WindowMode.panel`：桌宠形态下窗口只有立绘大小、透明无边框置顶；面板形态下同一窗口放大为 `1180×760` 的普通窗口。

理由：Flutter 桌面的多窗口支持仍是实验性的，而阶段 0 验收只要求「至少提供以下页面或面板」。同一窗口切换能一次性规避多窗口的焦点抢占、置顶互斥、托盘联动、退出竞态等一整类边界问题。切换本身用 `_pendingSwitch` 串行化，避免连点导致窗口尺寸抖动。

### 决策 B：进程 CPU / 内存 / 句柄采样走 **Dart FFI 直连 Win32**，不写 C++ 插件

需求允许「C++ 插件或 Dart FFI」。选 FFI 的原因：

- `GetProcessTimes` / `GetProcessMemoryInfo` / `GetProcessHandleCount` 都是**同一个进程内**的查询，无需跨进程；
- 不需要维护 `windows/` 下的 C++ 插件与插件注册，构建链更短、出错面更小；
- 采样本身只有 3 次 FFI 调用，开销可忽略，不会干扰被测对象；
- 非 Windows 平台自动退化为 `ProcessInfo.currentRss`（`Win32ProcessStats.isAvailable == false`），代码路径统一。

### 决策 C：**原始素材永不修改**，导入 = 复制到 AppData 托管目录

`emotion_assets` 同时保存 `file_path`（托管副本）与 `original_file_path`（用户原始路径）。删除素材只删托管副本。素材源目录 `Ace Attorney/` 在整个过程中保持**只读**。

### 决策 D：仓储抽象在外，实现可替换

`CharacterRepository` / `SettingsRepository` 是接口，`Sqlite*` 是阶段 0 实现。阶段 2 接服务端时，只改 `AppServices.bootstrap` 里的一行构造，业务代码零改动。

### 决策 E：所有业务表都带 `owner_id`

阶段 0 只有一个本地用户 `local.default`（`AppConstants.localOwnerId`），但表结构、索引、唯一约束都已经按多用户设计。服务端接入时不需要改表。

### 决策 F：平台能力缺口不允许中断启动

`WindowsWindowController.applySettings()` 对每个平台调用都包了 `_try(label, op)`：某个平台方法没实现（例如 `window_manager` 的 Windows 端没有注册 `setMovable`）时**记 warning 并降级**，而不是抛 `MissingPluginException` 把整个启动流程带崩。位置锁定因此改为在 Dart 侧生效（`PetView` 的 `onPanStart` 直接置空）。

### 决策 G：阶段 1 的 Win32 采集**沿用决策 B 的 Dart FFI 路径**

`GetForegroundWindow` / `GetWindowThreadProcessId` / `OpenProcess` /
`QueryFullProcessImageNameW` / `GetLastInputInfo` / `OpenInputDesktop` 全部走
`lib/activity_tracking/win32/win32_activity_native.dart`，理由与决策 B 一致：
不新增 C++ 插件、不动 `windows/` 脚手架与 CMake，构建链保持阶段 0 已验证的状态。

锁屏与会话状态**刻意不用** `WTSRegisterSessionNotification` / `RegisterSuspendResumeNotification`：
两者都需要真实窗口句柄，会侵入 runner 的窗口实现；而采集本身就是 2 秒轮询，
用 `OpenInputDesktop` + 「单调时钟 vs 墙上时钟」差值判定即可，成本可忽略。
详见 `10-Windows活动采集架构.md` §2、§4。

### 决策 H：状态映射是**纯函数**，防抖仍归阶段 0 的引擎

`ActivityStateMapper.decide()` 不读系统、不写库，只把「采集上下文」换算成「系统状态」，
因此 8 类分类 × 空闲 × 连续时长 × 今日用量 的组合可以被单元测试穷举。

**防抖、优先级、最短展示时长、等动画一轮**全部保留在阶段 0 的
`StateDebouncer` / `DefaultStateEngine` / `PetPresenter`，阶段 1 没有改写过它们。
自动状态一律以 `force = false` + `immediate = false` 发出，因此：

- `manual` 锁定依然绝对优先（引擎会在 `manual` 状态下拒绝一切 `force = false` 的请求）；
- 自动切换依然「等当前动画播完一轮」再淡入，不会打断动画。

### 决策 I：服务端与客户端是**两个独立可运行的单元**

客户端不导入任何服务端代码，服务端不读取客户端素材/日志；客户端在没有网络、
没有账号的情况下功能完整（这就是「无网络时桌宠和本地采集正常」这一验收项的设计基础）。
同步只能是**后台任务**，失败不得影响桌宠与本地计时。

### 决策 J：服务端把「隔离」与「隐私」做成结构保证，而不是代码纪律

- `activity_segments` 主键 = `(user_id, id)`、`daily_usage` 主键 = `(user_id, device_id, local_day)`：
  跨用户覆盖在**结构上**不可能；
- 隐私字段（窗口标题 / URL / 本地路径 / 截图）**表里根本没有这些列**，
  配合请求模型 `extra="forbid"`，误传会被 422 拒绝而不是静默入库；
- `app_key` 含路径分隔符直接拒绝（客户端应先规范化）；
- 以上都有机器断言（`test_migrations.py` / `test_isolation.py`），
  不依赖「记得加 where 条件」这种纪律。

## 6. 双形态窗口的边界

| 关注点 | 桌宠模式 | 控制面板模式 |
|---|---|---|
| 尺寸 | 按素材尺寸 × 缩放（默认 512×384） | 1180×760 |
| 可调整大小 | 否 | 是 |
| 标题栏 | 无（`MaterialType.transparency`） | 无，顶部自绘 46px 拖拽条 |
| 鼠标穿透 | 跟随设置 | 强制关闭（否则点不到按钮） |
| 位置锁定 | 跟随设置 | 强制关闭 |
| 入口 | 托盘菜单「控制面板」/ 右键菜单 | 顶部「回到桌宠」按钮 |

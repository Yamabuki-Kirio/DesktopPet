## 3. 设计层面的性能约束（代码保证，非实测曲线）

需求「十七、性能要求」的每一条都对应到具体实现：

| 要求 | 实现 | 落点 |
|---|---|---|
| 默认采样间隔 2 秒 | `ActivityTracking.sampleIntervalMs = 2000`，单个 `Timer.periodic` | `activity_tracker.dart` |
| 不得每次采样都全表查询 | 应用库（分类 + 排除名单）在启动时**一次性载入内存**，采样路径上零 SQL | `application_repository.dart` |
| 数据库写入使用事务与索引 | 建表语句含 `idx_activity_owner_time` / `idx_activity_owner_app` / `idx_activity_owner_device` / `idx_daily_usage_day`；批量写入走 `Batch` | `schema.dart` / `tracking_settings_dao.dart` |
| 统计查询不得阻塞桌宠主线程 | 统计只在用户打开统计页或点刷新时执行，且按 `(owner_id, started_at)` 索引做范围查询；右键菜单只读内存值 | `usage_analytics_service.dart` / `pet_view_wrapper.dart` |
| 采集不能导致动画卡顿 | 采集与渲染完全解耦：采样只做 Win32 调用 + 内存计算，每 30 秒才落盘一次；`ActivityTracker` 的每个 tick 都包在 try/catch 里，异常不会传播到渲染层 | `activity_tracker.dart` |
| 连续运行不增长内存/句柄 | 唯一的原生句柄（`OpenProcess` / `CreateToolhelp32Snapshot` / `OpenInputDesktop`）都在 `finally` 里 `CloseHandle` / `CloseDesktop`；`calloc` 分配全部成对释放；无任何列表随运行时长增长 | `win32_activity_native.dart` |
| 长时运行不累积磁盘写入 | 检查点是**覆盖写**（`segment_id` 为主键），`daily_usage` 是**覆盖写**（复合主键），因此写入量恒定，不随运行时长增长 | `activity_checkpoint_dao.dart` / `daily_usage_dao.dart` |

### 3.1 每秒成本估算

| 操作 | 频率 | 成本 |
|---|---|---|
| `GetForegroundWindow` + `GetWindowThreadProcessId` | 2 秒 1 次 | 微秒级 |
| `OpenProcess` + `QueryFullProcessImageNameW` + `CloseHandle` | 2 秒 1 次 | 微秒级 |
| `GetLastInputInfo` | 2 秒 1 次 | 微秒级 |
| `OpenInputDesktop` + `CloseDesktop` | 2 秒 1 次 | 微秒级 |
| `calloc` / `free` | 2 秒 3~4 次（几十字节） | 可忽略 |
| SQLite 写入 | **30 秒 1 次**（3~4 条覆盖写） | 毫秒级 |

因此桌宠空闲时的 CPU 增量应显著低于 1%（需求目标）。**但这需要以下实测确认。**

> 因此请按下表执行并回填。

### 4.1 执行前提

- `Ace Attorney` 已导入，Maya 动态 WebP 在桌宠窗口连续播放；
- 使用**本文件 §2.3 构建出的 Release 产物**，不要用 debug 版测性能。

### 4.2 执行步骤

1. 启动 `build\windows\x64\runner\Release\petlife.exe`；
2. 打开控制面板 →「诊断」页 → 点「开始采样（每 30 秒）」；
3. 按下列操作序列操作 **30 分钟**：

| 阶段 | 操作 | 观察点 |
|---|---|---|
| 0~5 分钟 | 在 VS Code / Word 等开发或办公软件中停留 | 桌宠 → `focused`；统计页「当前应用」在 3 秒内更新 |
| 5~10 分钟 | 切换到游戏或视频 | 桌宠 → `gaming` / `entertained` |
| 10~15 分钟 | 切换到浏览器 | 桌宠 → `default`（浏览器不猜测用途） |
| 15~20 分钟 | 离开电脑 ≥ 6 分钟（超过空闲阈值） | 桌宠 → `away`；活跃时间停止增长 |
| 20~22 分钟 | 回到电脑并继续操作 | 统计页出现**新的**活动段；`end_reason = user_idle` |
| 22~25 分钟 | 连续使用 ≥ 90 分钟已满足 → 观察 `tired` | 连续活跃满 90 分钟时切到 `tired` |
| 25~27 分钟 | 托盘或桌宠右键「暂停记录」，操作几秒后「恢复记录」 | 暂停瞬间当前段以 `tracking_paused` 结束 |
| 27~30 分钟 | 正常使用，期间锁屏一次再解锁 | 锁屏期间不计时；解锁后新开一段 |

4. 30 分钟后在诊断页点「导出 CSV + JSON」，并记录「实时 / 采样汇总」的数字；
5. 同时用任务管理器观察 `petlife.exe` 的内存、CPU、句柄数。

### 4.4 可用的交叉验证方式

即使不做满 30 分钟，以下方式也能在几分钟内验证核心正确性：

1. **数据库**：用任意 SQLite 工具打开 `<AppData>/PetLife/petlife.db`，执行

   ```sql
   SELECT app_key, datetime(started_at/1000, 'unixepoch', 'localtime') AS 开始,
          datetime(ended_at/1000, 'unixepoch', 'localtime')   AS 结束,
          active_seconds, end_reason
   FROM activity_segments ORDER BY started_at DESC LIMIT 20;
   ```

   检查：连续使用同一应用是否只有一行；`end_reason` 是否与你的实际操作一致；
   `active_seconds` 是否为负数或异常大（不应出现）。

2. **检查点**：`SELECT * FROM activity_checkpoints;` 应最多只有一行（当前段）。

3. **崩溃恢复**：在任务管理器里强制结束 `petlife.exe`，重新启动，
   确认上一次未关闭的段被标记为 `crash_recovery`，且 `active_seconds` 不超过崩溃前的实际使用时间。

4. **单实例**：连续双击两次 `petlife.exe`，第二个进程应立即退出，
   且在数据库里不会出现重复的时间段。

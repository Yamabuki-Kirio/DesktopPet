## 3. 缺陷 D-01 复盘：13 个素材全部导入失败（阻塞级，已修复）

### 3.1 现象

人工验收时导入 `Ace Attorney` 文件夹，界面与日志均为「扫描 13 个文件，**成功识别 0 个**，
损坏或跳过 13 个」。用户实际尝试了 3 次（文件夹导入、手动多选导入、文件夹导入），
三次结果一致（E9，`petlife.log` L88 / L142 / L171）：

```
19:53:01 [INFO]  petlife.scan: 素材扫描结束: 扫描 13 个文件，成功识别 0 个（动态 0 / 静态 0），损坏或跳过 13 个，耗时 32 ms
19:53:01 [WARNING] petlife.import: 导入单张图片失败: ...\Maya_Angry_1.webp | error=FormatException: The provided UUID is invalid.
   ...（13 条，逐文件一条）...
```

### 3.2 根因

`lib/core/ids.dart` 里的固定命名空间不满足 `uuid` 包的严格校验：

```dart
// 修复前
static const String namespace = '6f9619ff-8b86-d011-b42d-00c04fc964ff';
//                                        ^^^^ 第三段首字符是 d
```

`uuid` 4.6.0 的 `Uuid.v5()` 默认按 `ValidationMode.strictRFC9562` 校验命名空间
（`lib/validation.dart:54-61`），其形态要求等价于：

```
^[0-9a-f]{8}-[0-9a-f]{4}-[0-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$
```

- 第三段首字符必须落在 `0-8`（**version 位**）→ 实际是 `d`，**非法**；
- 第四段首字符必须落在 `8/9/a/b`（variant 位）→ 实际是 `b`，本来就合法。

于是 `Uuid.v5()` 抛 `FormatException: The provided UUID is invalid.`。
导入链路里第一个 ID 调用是 `Ids.packId()`（在 `ensurePack()` 内部），
因此**每个文件都在写库之前就抛异常**，被 `_importFolder` 的 per-file `try/catch`
捕获后记为「失败」——这既解释了 13/13 全失败，也解释了为什么失败信息是
`FailureKind.unknown / 导入失败` 而不是某种素材损坏。

### 3.3 测试缺口（本轮的关键结论）

**ID 层此前完全没有测试覆盖。** 原有的 37 个测试分布在文件名解析、WebP 容器解析、
状态引擎三块，都只用到「已解析出的字符串」，从不调用 `Ids.*`。
而 ID 是导入路径的**第一道门**，它坏了会导致整条链路 100% 失败 —— 一个
「零成本可测、却零覆盖」的模块，拖到人工验收才暴露。

同类缺口还有一处：**导入链路没有端到端测试**（只有离线的容器解析测试），
因此「扫描到 13 个但一个都进不了库」这件事也无法被自动发现。

### 3.4 修复内容

| 文件 | 改动 |
|---|---|
| `lib/core/ids.dart` | 命名空间改为 `6f9619ff-8b86-4011-b42d-00c04fc964ff`（只修正非法的 version 位，variant 位沿用原值，改动面最小）；新增 `Ids.isNamespaceValid` 与 `Ids.assertNamespaceValid()`，并写明「一旦有用户数据即永不可变」 |
| `lib/app/app_scope.dart` | 装配第 0 步调用 `Ids.assertNamespaceValid()`：命名空间非法时**启动即报错**，不再等到用户点导入才逐条失败 |
| `test/ids_test.dart`（新增） | 23 项：命名空间合法性（D-01 回归护栏）、4 个生成器不抛异常、确定性、唯一性、合法 UUID v5、13 个真实文件 ID 互异 |
| `test/asset_import_integration_test.dart`（新增） | 3 项：真实文件夹导入 13/13 + 二次导入幂等、事务回滚不留孤儿、事务提交可见 |
| `test/support/sqlite_test_bootstrap.dart`（新增） | 让 `flutter test` 能加载 sqlite3 原生库（详见 §3.6） |

> **为什么现在改命名空间是安全的**：`character_packs` / `character_models` / `emotion_assets`
> 三张表当时**都是 0 行**（E10），没有任何持久化素材 ID 依赖旧值。
> 一旦有用户数据，这个常量就永不可再变 —— 它是 uuid v5 的输入之一，
> 改动会让全部 ID 漂移、用户状态映射全部失效。这一点已写进 `ids.dart` 的注释。

### 3.6 一个必须说明的测试环境限制

集成测试要访问真实 SQLite。但 `sqlite3` 3.6 走 native assets 的
`DynamicLoadingSystem`，运行期按**名字**加载 `sqlite3.dll`；测试宿主
`flutter_tester.exe` 位于 Flutter SDK 缓存目录，旁边没有这个 DLL，裸跑必然失败：

```
Failed to load dynamic library 'sqlite3.dll' (error code: 126)
```

`test/support/sqlite_test_bootstrap.dart` 的解法：按优先级找可用库
（环境变量 `PETLIFE_SQLITE3_DLL` → 本工程 Release 产物 → `%SystemRoot%\System32\winsqlite3.dll`），
**统一改名为 `sqlite3.dll`** 暂存到临时目录，再用 `SetDllDirectoryW` 把它加入 DLL 搜索路径。
全程不修改工程与 SDK 目录，幂等可重复。

> 找不到库时**不会静默跳过**，而是抛错并列出所有尝试过的候选路径 ——
> 否则「数据库测试全部消失」会被误读成「全部通过」，这正是 D-01 漏检的同一类问题。

## 4. 缺陷 D-02 复盘：增量构建失败在插件软链接（构建环境，已修复）

### 4.1 现象

缺陷 D-01 修复后执行增量构建，失败（E14）：

```
Flutter failed to create a link at "...\windows\flutter\ephemeral\.plugin_symlinks\path_provider_windows"
  to "...\pub.dev\path_provider_windows-2.3.0\". The file or directory could not be found.
PathNotFoundException: Cannot create link ... (OS Error: 系统找不到指定的文件。, errno = 2)
build_exit=1
```

### 4.2 根因

本机存在一个已知的「`Link.createSync` 抛伪异常」问题（`06-...md` §6.1），
它需要靠手工补链脚本绕过。而本次的报错**长得几乎一样**，极易误判为同一个问题，
但根因完全不同：补链脚本此前只从 `windows/flutter/generated_plugins.cmake`
读取清单（5 个插件），而 Flutter 工具实际要求 **7 个**软链接 ——
漏掉的两个是 **Dart-only 插件** `path_provider_windows` 与 `file_picker`
（pubspec 里是 `dartPluginClass`，没有 `windows/` 目录，因此不进 CMake，但仍然需要链接）。

### 4.3 修复内容

| 文件 | 改动 |
|---|---|
| `.workbuddy/tmp/link_plugins.dart`（构建脚本） | 插件清单改为取 **`.flutter-plugins-dependencies` 的 `plugins.windows[*]`**（权威来源）与 `generated_plugins.cmake` 的**并集**；目标路径优先取前者的绝对路径，缺失才回退 `package_config.json`；输出里标注每个插件是「有原生代码」还是「Dart-only」；最后单独校验「CMake 需要的插件是否都有链接」 |
| `docs/06-构建运行手册与开发环境.md` §6.1 | 纠正了原来「只补 5 个就够了」的错误结论，补充 7 个插件的完整表格、真实报错原文，以及「如何区分伪异常与真缺失」的判别方法 |

重建结果：7/7 链接就绪，`√ Built ...petlife.exe`，62.3 s，`exit=0`。

### 9.2 阶段 0 收尾中发现并修复的两个阻塞缺陷

人工 GUI 验证曾暴露两个缺陷，均已修复并补测试：

| 缺陷 | 根因 | 修复 | 回归覆盖 |
|---|---|---|---|
| **动态 WebP 显示但完全不动** | `_PetLayerPainter.shouldRepaint()` 用 `identical(a.image, b.image)` 判断重绘。而 `AnimationRenderLayer.image` 是**实时 getter**，新旧 Painter 读到的是同一个可变 `DecodedAnimation` 的当前帧，`identical` 恒为 true → 永不重绘 | 只要存在动画图层就一律返回 `true` 重绘：帧定时器只在 `advance()` 真正推进后才 `notifyListeners()`，静态图（`frameCount == 1`）根本不启动定时器，因此不会造成静态图持续重绘 | `test/pet_animation_repaint_test.dart`（10 项：帧推进、通知、Painter 重绘、静态图不启定时器、`loopAnimation=false` 停帧、切换素材释放旧 `ui.Image`） |
| **状态调试器点击后反应很慢** | 调试器用 `immediate: state.isUrgent`，非紧急状态会等当前动画播完一轮（最长约 6.6 秒） | 状态调试器是人工验证工具，所有手动触发改为 `force: true` + `immediate: true`。**自动状态切换仍保留 `immediate = false`** 的平滑规则 | `debuggerStateRequest()` 抽出为可测函数；断言 11 个状态全部携带 `force=true`/`immediate=true`，且自动状态仍 `waitForAnimationCycle=true` |

两个缺陷的共同教训是：**只测「逻辑返回值」测不出「真的有没有画出来」**。
因此阶段 1 的测试刻意覆盖了「段真的落库了吗、检查点真的写了吗、迁移真的保住老数据了吗」
这类**副作用断言**，而不是只断言函数返回了什么。

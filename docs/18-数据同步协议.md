# 18 · 数据同步协议

> 服务端实现见 `server/app/services/sync_service.py`、`server/app/schemas/sync.py`。

## 1. 同步范围

| 实体 | 本地来源 | 服务端主键 | 同步语义 |
|---|---|---|---|
| 活动段 | `activity_segments` | `(user_id, id)`，`id` 为**客户端稳定 UUID** | 逐条 upsert + Last-Write-Wins |
| 每日用量 | `daily_usage` | `(user_id, device_id, local_day)` | **整行快照覆盖**（不累加） |
| 应用库 | `applications` | `(user_id, app_key)` | 人工分类优先，否则按 `updated_at` |
| 设备信息 | `devices` | `id` | 通过 `/devices/register` 注册/更新 |
| 同步元数据 | `sync_state` / `sync_outbox` | — | 只存在于客户端 |

**明确不上传**（服务端连字段都没有，误传会被 422 拒绝）：

- 窗口标题、文档名称、浏览器网页标题、浏览器 URL
- 本地完整文件路径（含素材路径与可执行文件路径）
- 用户输入内容、截图、剪贴板、键盘记录
- 素材文件本身、日志文件

## 2. push：批量上传

```http
POST /api/v1/sync/push
Authorization: Bearer <access>
X-Device-Id: <server device uuid>
Content-Type: application/json

{
  "batch_id": "可选，用于日志关联",
  "activity_segments": [
    {
      "id": "客户端生成的 UUID",
      "device_id": "本设备的服务端 UUID",
      "app_key": "code",
      "category": "development",
      "started_at": "2026-09-27T10:00:00Z",
      "ended_at": "2026-09-27T10:42:15Z",
      "active_seconds": 2535,
      "end_reason": "foreground_changed",
      "created_at": "2026-09-27T10:00:00Z",
      "updated_at": "2026-09-27T10:42:15Z"
    }
  ],
  "daily_usage": [
    {
      "device_id": "本设备的服务端 UUID",
      "local_day": "2026-09-27",
      "timezone_offset_minutes": 480,
      "session_seconds": 18000,
      "active_seconds": 14400,
      "idle_seconds": 3600,
      "first_active_at": "2026-09-27T01:12:00Z",
      "last_active_at": "2026-09-27T11:50:00Z",
      "updated_at": "2026-09-27T12:00:00Z"
    }
  ],
  "applications": [
    {
      "app_key": "code",
      "display_name": "Visual Studio Code",
      "category": "development",
      "user_overridden": false,
      "updated_at": "2026-09-27T12:00:00Z"
    }
  ]
}
```

响应 `200`：

```json
{
  "batch_id": "...",
  "accepted_activity_segments": 1,
  "accepted_daily_usage": 1,
  "accepted_applications": 1,
  "accepted_total": 3,
  "rejected": [],
  "server_time": "2026-09-27T12:00:05Z",
  "cursor": 42
}
```

`rejected[]` 的结构（单条失败不影响同批其他记录）：

```json
{"kind": "activity_segment", "key": "<记录 id>", "code": "invalid_time_range",
 "message": "ended_at 早于 started_at"}
```

### 2.1 幂等性保证

| 机制 | 保证 |
|---|---|
| 活动段主键 `(user_id, id)` | 重复上传同一 UUID 命中同一行 → **不会重复** |
| 每日用量复合主键 | 同一 `(device, day)` 只有一行 → **不会重复累计** |
| 应用库复合主键 | 同一 `app_key` 只有一行 |
| 每条记录一个 SAVEPOINT | 单条失败只拒绝该条，不回滚整批 |
| `batch_id` | 仅用于日志关联与排查；**幂等不依赖它**，而依赖主键 |

实测（`tools/e2e_smoke.py`）：提交同一批次两次，`accepted_total` 都是 5，
下拉后的活动段仍为 3 条、每日用量 1 条、应用 1 条，统计数字不变。

### 2.2 批量与校验

| 规则 | 行为 |
|---|---|
| 单批总量 > `PETLIFE_SYNC_MAX_BATCH_SIZE`（默认 200） | `413 batch_too_large` |
| 单批 = 200 | 正常接受（有测试覆盖） |
| 记录里的 `device_id` ≠ 当前设备 | 该条被拒 `invalid_batch` |
| `ended_at < started_at` | 该条被拒 `invalid_time_range` |
| `id` 不是合法 UUID | `422 invalid_uuid` |
| `app_key` 含 `\` 或 `/` | `422 validation_error`（隐私防线） |
| 出现未知字段（如 `window_title`） | `422 validation_error`（`extra="forbid"`） |
| `local_day` 非法（如 `2026-02-30`） | `422` |
| `timezone_offset_minutes` 超出 `-720~840` | `422` |
| `active_seconds` 为负或 > 2 天 | `422` |

## 3. pull：增量拉取

```http
GET /api/v1/sync/pull?cursor=0&limit=500[&device_ids=<uuid>&device_ids=<uuid>]
Authorization: Bearer <access>
X-Device-Id: <server device uuid>
```

响应：

```json
{
  "cursor": 57,
  "has_more": false,
  "activity_segments": [...],
  "daily_usage": [...],
  "applications": [...],
  "server_time": "2026-09-27T12:00:05Z"
}
```

### 3.1 游标机制

- 每张可同步表都有 `change_seq`，取值来自 `sync_log.seq`（单表自增主键）；
- `pull` 返回 `change_seq > cursor` 的记录，按 `change_seq` 升序；
- 新游标 = 本次返回记录中最大的 `change_seq`（没有新数据时**原样返回入参**，
  保证"游标只增不减"）；
- `has_more` 表示某一类记录触到了 `limit`，客户端应继续用新游标拉取直到 `false`。

默认返回该账户**全部设备**的数据（新设备据此完成首次全量对齐）；
传 `device_ids` 可只拉指定设备。**只返回当前用户的数据**——
隔离由 `WHERE user_id = ?` 保证，并有专门的测试文件 `test_isolation.py`。

### 3.2 客户端建议的调用节奏

| 触发时机 | 说明 |
|---|---|
| 登录成功后 | 先 pull 对齐游标，再 push 本地积压 |
| 应用启动后 | 同上 |
| 网络恢复后 | 重置退避并立即尝试 |
| 用户点「立即同步」 | 立即执行 |
| 后台定时 | 建议 5 分钟一次 |
| 程序退出时 | 可做一次**短时**同步，不能长时间阻塞退出 |

## 4. 冲突策略

### 4.1 活动段：Last-Write-Wins

同一 `(user_id, id)` 视为同一记录，`updated_at` 较新者胜。
旧记录到达时被静默忽略（仍计入 `accepted`，因为它确实被"处理"了）。
有测试 `test_activity_segment_last_write_wins` 覆盖两个方向。

### 4.2 每日用量：整行快照覆盖

**不做秒数累加**。原因：网络超时但服务端已写入时客户端会重传，
若是累加就会重复计数。改成覆盖后，重传同一份快照是幂等空操作。

判定：`updated_at >= 已存行的 updated_at` 才覆盖（用 `>=` 而不是 `>`，
让"重传同一份快照"成为安全的空操作）。有测试
`test_daily_usage_resend_does_not_double_count` 连续重传 4 次并断言秒数不变。

### 4.3 应用库：人工分类优先

```
if 已存行 user_overridden 且 新记录 user_overridden=false  → 保留已存行
if 新记录 user_overridden=true 且 已存行 user_overridden=false → 采用新记录
否则 → 按 updated_at 较新者胜
```

即**用户手工分类优先于内置分类**，即使内置分类的记录时间更新也不能覆盖。
有测试 `test_application_manual_category_beats_builtin` 覆盖。

### 4.4 跨用户

**不允许**任何跨用户读写。实现上不是靠"记得加 where 条件"，
而是把 `user_id` 放进主键 / 查询条件的第一位；
`test_replaying_another_users_record_id_cannot_overwrite` 验证了
「B 重放 A 的记录 UUID」只会写入 B 自己名下，A 的数据一字不改。

## 5. 客户端 outbox 模型（已实施）

> 实现：`lib/sync/outbox_producer.dart`、`lib/sync/sync_engine.dart`、
> `lib/database/dao/sync_outbox_dao.dart`、`lib/database/dao/sync_state_dao.dart`。
> 表结构见 `05-数据库设计与迁移.md` §8。

| 客户端表 | 用途 |
|---|---|
| `sync_outbox` | 待上传记录（`id` 稳定 UUID / `entity_type` / `entity_key` / `entity_local_id` / `operation` / `payload_json` / `attempt_count` / `next_attempt_at` / `last_error` / `acknowledged_at`） |
| `sync_state` | 每类实体的 `cursor`、`last_success_at`、`last_error`、`consecutive_failures`、`next_retry_at` |
| `account_session_state` | 服务端地址、用户信息、`credential_reference`、设备 UUID（**不含令牌**，见 `19-隐私与安全说明.md` §7） |

### 5.1 关键规则（与实现一一对应）

1. **本地写入永远先成功**，再把 outbox 记录入队；两者在同一业务流程中，
   采集事务**不会**等待任何网络操作（`LocalChangeSink` 回调只做本地入队）。
2. 只有收到服务端 `accept`（或明确为该条的 `rejected`）才把 `acknowledged_at` 置位。
3. 网络失败**不丢数据**，只增加 `attempt_count` 并设置 `next_attempt_at`。
4. 指数退避：5s → 15s → 1min → 5min → 15min，上限 1 小时。
5. Access Token 过期 → 自动刷新并**重试一次**（重试深度由编译期参数固定，不可能无限循环）。
6. Refresh Token 失效 → 进入「需要重新登录」状态，**本地采集继续运行**。
7. 同一设备同时只有一个同步任务在跑（互斥；计时器重入不会启动第二个）。

### 5.2 用稳定 UUID 而非自增 ID

`sync_outbox.id` 与活动段的远程主键都是**稳定 UUID**：
活动段的 `id` 由 `Ids.segment(owner, device, app_key, 起点毫秒)` 确定性生成，
因此"同一段被处理两次"得到的是同一个 UUID，服务端 upsert 命中同一行。

### 5.3 幂等排队靠数据库约束，不靠应用层判断

`sync_outbox` 上有一条**部分唯一索引**：

```sql
CREATE UNIQUE INDEX uq_sync_outbox_pending_entity
    ON sync_outbox (entity_type, entity_key) WHERE acknowledged_at IS NULL;
```

同一 `(entity_type, entity_key)` 在"未确认"状态下最多只有一行。
重复入队走 `ON CONFLICT ... DO UPDATE`，**刷新 payload 但保留 `attempt_count` 与 `next_attempt_at`**
（否则每次重新入队都会把退避清零，失败记录变成忙等重试）。
重复确认（`acknowledge`）只影响 `acknowledged_at IS NULL` 的行，因此天然幂等。

### 5.4 payload 在推送时重建

`sync_outbox.payload_json` 入队时写一份，但 `OutboxProducer.buildPayload()` 在**推送前**
按 `entity_key` 回查本地业务表**重新构造** payload：

- `daily_usage` 永远上传**当前完整快照**，天然满足"不做增量累加"；
- 活动段的 `updated_at` 取自 `ended_at`（进行中的段取"现在"），走到 `updated_at` 的 LWW 判定时符合预期；
- 应用库记录**不带 `device_id`** —— 服务端 `AppRecordIn` 是 `extra="forbid"`，
  多塞一个字段会整条 422 被拒（这一点是联调时由测试真实发现的）。

### 5.5 批量与历史数据

| 规则 | 实现 |
|---|---|
| 每批最多 200 条 | `SyncConfig.maxBatchSize`，与 `PETLIFE_SYNC_MAX_BATCH_SIZE` 默认值一致 |
| 一次同步最多多少批 | `SyncConfig.maxBatchesPerRun = 20`，防止一次同步跑太久 |
| 首次登录的历史数据 | `OutboxProducer.enqueueHistory()` 把既有 `activity_segments` / `daily_usage` / `applications` 入队，上限 `historyBackfillLimit = 20000` 条，用 `sync_state.cursor` 标记避免重复回填 |
| 禁止上传的字段 | payload 白名单构建，逐字段显式挑选；窗口标题 / URL / 路径 / 截图 / 素材 / 日志**结构上不可能出现**（测试用 `expect(payload.keys.toSet(), {...})` 精确断言） |

## 6. 错误处理与重试

| 服务端返回 | 客户端动作 |
|---|---|
| `200` + `rejected[]` | 把 `rejected` 里"不可恢复"的条目丢弃并记日志；`conflict` 类可以重试 |
| `401 token_expired` | 刷新后重试一次 |
| `401 token_invalid` / `refresh_token_reused` | 进入「需要重新登录」，停止 push，**本地采集不停** |
| `403 device_revoked` | 同上，并提示用户该设备已被撤销 |
| `413 batch_too_large` | 拆成更小的批次重试 |
| `5xx` / 网络错误 | 指数退避重试，不丢数据 |

普通网络错误只在「账户与同步」页面与日志里展示，**不弹窗**——
需求明确要求「界面不得因为同步失败持续弹窗」。

## 7. 服务端统计接口

| 接口 | 返回 |
|---|---|
| `GET /stats/summary?period=&tz_offset_minutes=` | 屏幕会话 / 活跃 / 空闲 / 应用使用时间、设备数、首次与最后活跃 |
| `GET /stats/devices` | 每台设备的使用时长 + 合计（带重叠提示） |
| `GET /stats/apps` | 各应用使用时长 + 段次数 + 占比 |
| `GET /stats/categories` | 各分类使用时长 + 占比 |

`period ∈ today | yesterday | 7d | 30d`。

口径与客户端完全一致（见 `12-使用统计口径.md`）：

- 与窗口有交集的活动段按**墙钟比例折算**，跨零点的那段被正确拆到两天，
  两天之和等于原值；
- `应用使用时间 ≤ 活跃使用时间`；
- **时区由客户端的 `tz_offset_minutes` 决定**，服务端不按自己的时区算"今天"；
- 多设备合计是**求和**，`overlap_warning` 字段明确提示"未做去重"
  （不同设备并行使用时时间会重叠），绝不偷偷去重。

实测（`e2e_smoke.py`）：上传 3 段（各 1800s）+ 每日用量（活跃 4h / 空闲 1h）后，
`summary` 返回活跃 4h、空闲 1h、会话 5h、应用使用 5400s、设备数 1，
且 5400 ≤ 14400 满足口径约束。

## 8. 客户端同步引擎（已实施）

实现：`lib/sync/sync_engine.dart`。UI 与采集层都不直接调用 HTTP，
全部经由 `SyncEngine` → `AuthenticatedApi` → `ApiClient` 三层，其中只有
`AuthenticatedApi` 接触令牌。

### 8.1 触发时机

| 触发 | 入口 | 说明 |
|---|---|---|
| 登录并完成设备注册后 | `onSignedIn()` | 先回填历史数据，再立刻同步一次 |
| 应用启动后 | `start()` | 只在已恢复登录时跑 |
| 每 5 分钟 | `SyncConfig.periodicInterval` | 定时器 |
| 用户点「立即同步」 | `syncNow(manual: true)` | 手动触发**忽略退避等待**，立即尝试 |
| 网络恢复后 | `onNetworkRestored()` | 重置退避 |
| 程序退出前 | `syncOnShutdown()` | **严格超时 `SyncConfig.shutdownTimeout = 5s`**，超时后不再等待 |

### 8.2 状态机

| 状态 | 含义 | `keepsLocalTracking` |
|---|---|---|
| `signedOut` | 未登录 | ✅ |
| `idle` | 已登录、无任务在跑 | ✅ |
| `syncing` | 正在同步 | ✅ |
| `success` | 上次同步成功 | ✅ |
| `waitingForNetwork` | 服务端不可达 / 超时，等待退避 | ✅ |
| `needsReauthentication` | 令牌失效 / 设备被撤销，需重新登录 | ✅ |
| `failed` | 其它错误（如响应格式错误） | ✅ |

七种状态**全部**保持本地采集运行 —— 这是"普通网络异常不得影响桌宠和本地采集"这条要求的落点，
并在 `test/sync_engine_test.dart` 与真实联调的 `offline` / `revoked` 两个阶段都被验证。

### 8.3 单任务互斥与退避

- `_syncOnce()` 先检查 `_inFlight`：已有任务在跑就**复用同一个 Future**，不启动第二个；
- 退避阶梯由 `computeBackoff(failures)` 计算：5s / 15s / 60s / 300s / 900s，超出取最后一档；
  `maxBackoffSeconds = 3600` 作为上限；
- 手动同步与网络恢复会**清空退避**（`next_retry_at` 归零），避免用户点了按钮却"什么也没发生"；
- 失败时同样会 `refreshPendingCount()`，否则界面会显示"待同步 0 条"造成误判。

### 8.4 退出前同步不阻塞退出

`syncOnShutdown()` 用 `task.timeout(...)` 包住同步任务，超时后：
先 `unawaited(task.then(_, onError: ...))` **吞掉超时后仍在飞的请求可能抛出的异常**，
再记一条日志返回。因此进程绝不会因为一个卡住的 HTTP 请求而挂住不退。

## 9. 真实端到端联调实测（客户端 ↔ 真实服务端）

脚本：`tools/e2e_client_sync.ps1`（PowerShell，纯 ASCII），用例：`test/e2e_real_server_test.dart`。
**不是 mock**：真实启动 uvicorn + 真实 SQLite/PostgreSQL 兼容层，客户端走真实 HTTP + 真实凭据后端。

因为「单个 `flutter test` 进程无法在两次客户端运行之间起停服务端」，
联调拆成 5 个阶段（各自独立的 `flutter test` 调用），共享同一个
`build/e2e/e2e.db`（等价于"关掉客户端再打开"）：

| 阶段 | 覆盖的验收动作 | 实测结果 |
|---|---|---|
| `online` | 启动服务端 → 注册并登录 → 注册设备 → 产生新活动记录 → 立即同步 → 服务端查询确认 → 重复同步确认无重复 | 设备数 1、应用数 2、应用使用 **420s**；重复同步后仍 **420s**（= 300 + 120，无重复统计） |
| `offline` | 停掉服务端 → 继续使用客户端并产生本地记录 | 状态 = `waitingForNetwork`，待同步 **3 条**，本地活动段 **4 条**（采集未停） |
| `recover` | 恢复服务端 → 确认自动补传 | 待同步 3 → **0**；服务端应用使用 **840s**（= 420 + 240 + 180，与本地一致） |
| `revoked` | 从另一会话撤销当前设备 | 状态 = `needsReauthentication`，**本地活动段 5 条**（采集继续），待同步 2 条 |
| `signout` | 退出登录 | 凭据已删除（`credentials.read('PetLife:account')` 返回 null），本地活动段 **6 条**、待同步 3 条**保留** |

凭据后端实测识别为 **Windows Credential Manager**。

> ⚠️ 该脚本需要本机可运行 `server/`（嵌入式 Python + 迁移已完成）。
> 若在没有服务端运行环境的机器上执行，请先按 `16-服务端部署与配置.md` 准备。
> 真实 PostgreSQL + docker compose 的组合**未在本机验证**，见 `20-Phase2测试与验收报告.md`。

## 10. 代理与传输（协议无变化）

代理支持**不修改**本文件的任何请求/响应结构、认证流程或冲突策略 ——
它只决定「socket 怎么建起来」。对服务端来说，经代理来的请求与直连请求完全一样。

### 10.1 四种连接方式

| 模式 | 行为 |
|---|---|
| `automatic`（默认） | 读 Windows 当前用户代理（WinHTTP → 注册表回退）。检测到静态 HTTP 代理就用；否则**退回直连** |
| `system` | 强制使用 Windows 系统代理。检测不到时给出**明确错误**并退回直连（不静默） |
| `manualHttp` | 用配置里的 `host:port`（Clash HTTP/Mixed Port，例如 `127.0.0.1:7877`） |
| `direct` | 强制直连，忽略任何系统代理 |

决策结果最终落到 `HttpClient.findProxy`：

```dart
// 直连
'DIRECT'
// 经代理
'PROXY 127.0.0.1:7877'
```

`bypassLocalhost`（默认开）对应 Windows 的 `<local>` 语义：回环地址与**不含点**的
主机名直接连，不经代理。

### 10.2 所有请求共用同一个出口

`health` / 注册 / 登录 / 刷新 / 注销 / 设备注册 / 设备列表 / 改设备 / 撤销设备 /
`sync push` / `sync pull` / 统计 —— **全部**由 `AuthenticatedApi` 里同一个
`ApiClient` 发出，因此共享同一份代理配置。
需求明确禁止"只让登录走代理、同步仍然直连"，这一点由结构保证（只有一处建 client 的地方）。

**配置变化必须重建连接池**：`AuthenticatedApi.applyProxySettings()` 会
`close(force: true)` 掉旧 `HttpClient` 再新建，因为旧连接池里可能还留着按老路由建立的连接。
`networkGeneration` 计数用于断言这次重建确实发生了。

### 10.3 新增的失败分级

代理引入了几种新的失败类型（`SyncFailureKind`），它们在 UI 上的措辞与处置都不同：

| 类型 | 触发 | 是否重试 | UI 状态 |
|---|---|---|---|
| `proxyUnreachable` | 连不上代理（Clash 没开、端口错） | ✅ 退避重试 | 等待网络 |
| `proxyAuthRequired` | 代理返回 407 且无可用凭据 | ❌ | 同步失败（提示去填代理账号） |
| `tlsHandshakeFailed` | 证书校验或握手失败 | ✅ 退避重试 | 等待网络 |

**这几种都保持本地采集继续运行** —— 与原来的网络失败一致。

### 10.4 分阶段探测（界面上四个按钮）

| 按钮 | 做的事 |
|---|---|
| 检测系统代理 | 只读 WinHTTP / 注册表，显示检测到的 `ProxyServer` 与来源 |
| 测试代理 | TCP 连代理 → `CONNECT` 隧道（读状态行，能识别 407） |
| 测试服务端 | TCP → `CONNECT` → TLS 握手 → `GET /health` |
| 保存并重新连接 | 写偏好 → 重新解析决策 → 重建 `HttpClient` |

CONNECT 阶段刻意用**裸 socket** 手工发请求，因为 `HttpClient` 只会抛一个笼统异常、
拿不到 `407` 这种状态码；TLS 与 `/health` 阶段则交回 `HttpClient`
（这样证书校验保持 Dart 默认行为，**不做任何绕过**）。
